## Proposal 1: two Sprint Boundary Checklist items name artifacts no scaffold creates, so both are unsatisfiable by default and silently waivable

**Type:** Backlog Proposal (methodology defect)
**Priority:** Medium

**Problem statement.** DSM_2.0.C §1 Template 8's Sprint Boundary Checklist contains two
items that reference a specific path:

- Item 5: "`dsm-docs/guides/smoke-tests.md` current (or N/A if no smoke tests recorded
  this sprint)"
- Item 7: "Blog publication tracker updated (`dsm-docs/blog/README.md`)"

Neither path is created by `/dsm-align` Step 3's canonical folder scaffolding, nor by any
other skill. A spoke therefore reaches its first sprint boundary with both items pointing
at things that do not exist.

**Why this is worse than a missing file.** The two items fail differently, and both
failures are silent:

- Item 5 carries an "or N/A" escape clause. So it is *always* tickable, forever, without
  the file ever being created. The check can never fire. In this repository it had been
  ticked or deferred across every sprint since the checklist was adopted, and the S57
  checkpoint recorded it as "never actionable", which was itself an overstatement: it was
  always actionable as N/A, which is exactly the problem.
- Item 7 has no escape clause and is simply impossible. `dsm-docs/blog/README.md` exists
  in this repo but contained a structure diagram and a file-naming table, with no tracker
  of any kind. You cannot "update a publication tracker" that was never a tracker. An
  agent ticking this item is either not reading it or quietly redefining it.

The common shape: **a checklist item that names a path the scaffold does not create is
unsatisfiable-by-default in every spoke, and looks tickable.**

**Observed S58.** Resolved locally by creating `dsm-docs/guides/smoke-tests.md` with seven
executed checks, and by adding an actual publication tracker to `dsm-docs/blog/README.md`.
Writing the smoke tests immediately surfaced three defects that had gone unnoticed
precisely because no smoke test existed: `README.md` claimed version 0.4.0 while
`pyproject.toml`, the `click.version_option` literal and the installed package all said
0.3.0; `python -m cli` exits 0 and does nothing (no `__main__` guard), so it looks like a
passing run; and the knowledge summary emits `## Document Hierarchy` where the vision
calls that component "Project Map".

**Suggested resolution.** Pick one of:

1. Have `/dsm-align` scaffold both artifacts as stubs, so the items become live checks
   rather than permanent waivers. A `smoke-tests.md` stub with a "no smoke tests recorded"
   header is enough; the point is that the file exists and can go stale visibly.
2. Reword both items so they do not name a path the scaffold does not guarantee, e.g.
   "Smoke tests recorded, or explicitly N/A with a reason" and "Blog publication status
   recorded".

Option 1 is preferred: it keeps the paths canonical and makes the checks real. Option 2 is
cheaper but leaves each spoke to invent its own location.

**Generalisation worth checking at Central:** this is a two-instance sample of a class.
An audit of Template 8 (and any other checklist) for items naming non-scaffolded paths
would likely find more.

## Proposal 2: a second skill asserts its state files are gitignored while the filesystem has them tracked, so this is a class defect rather than a one-off

**Type:** Backlog Proposal (documentation defect)
**Priority:** Medium

**Problem statement.** `scripts/commands/dsm-staa.md` states that
`.claude/reasoning-lessons.md`, `.claude/reasoning-lessons-compact.md` and
`.claude/last-staa.txt` are "gitignored local-only artifacts; none is committed". In this
repository all three return exit 0 from `git ls-files --error-unmatch`, and none is matched
by `.gitignore` (which does list `.claude/session-baseline.txt`, `.claude/session.lock`
and `.claude/cross-repo-writes-session.txt`).

**Why this is being raised again.** This is the **second instance in two sessions**. S57
Proposal 2 reported the identical shape for a different skill: `/dsm-align` describes
`last-align.txt` and `last-align-report.md` as gitignored, and in this repo they are
tracked. Two skills, same false claim about repository state, found independently. That
moves it from "fix the sentence in `/dsm-staa`" to a question about whether skill
documentation should assert repo state at all.

**Consequence.** The claim drives behaviour. An agent that believes these files are
gitignored will not use an explicit pathspec when committing, so a skill's output rides
into an unrelated commit. Here the S57 STAA run left three modified files in the working
tree that a later commit would have silently absorbed.

**Verify:**

```bash
git ls-files --error-unmatch .claude/reasoning-lessons.md \
  .claude/reasoning-lessons-compact.md .claude/last-staa.txt
git check-ignore -v .claude/reasoning-lessons.md   # no output = not ignored
```

**Local resolution (S58).** Keep them tracked, and correct the skill text rather than the
repository. Tracking has concrete value that the skill's contract overlooks: version
history is what made the S57 STAA run's own nine-entry prune safe to perform without a
backup file. Committed on a dedicated commit.

**Suggested resolution.** Either (a) correct both skills' text to describe these as
"local-state artifacts, tracked or gitignored per project", and add an explicit
"commit with a pathspec" instruction, or (b) have `/dsm-align` reconcile `.gitignore`
against the skills' stated contract so the assertion becomes true by construction. (a) is
lower-risk; (b) would have destroyed recoverable history here, so if (b) is chosen it
needs an opt-out.

## Proposal 3: `/dsm-go` Step 5.8's incomplete-wrap-up detection is a false positive by construction on every normal session start

**Type:** Backlog Proposal (skill logic defect)
**Priority:** Low

**Problem statement.** Step 5.8 says:

> Detect whether the previous session ended without a full wrap-up by comparing MEMORY.md's
> "Latest Session" number against the current branch session number (extracted from the
> branch name, e.g., `session-139/...` → 139). If the branch number > MEMORY number, the
> previous session had an incomplete wrap-up.

But Step 0a computes the new session number as
`N = max(ARCHIVE_COUNT, MEMORY_SESSION_NUMBER, REMOTE_SESSION_COUNT) + 1`, and Step 0c
creates the branch `session-{N}/{date}`. So on any boot that creates a fresh branch, the
branch number is **always** greater than the MEMORY number, by construction. The stated
condition is satisfied on every normal session start.

**Observed S58.** Branch `session-58/2026-08-04`, MEMORY latest session 57, so 58 > 57 and
the condition fired. The previous session had in fact wrapped up fully. What resolved it
was a corroborating signal the step does not mention: `.claude/last-wrap-up.txt` reading
`session: 57 / type: full`.

**Why it has not caused visible harm.** Agents appear to reach for `last-wrap-up.txt` or
notice the situation is normal, and the step's remedy is a prompt rather than an action.
The cost is a spurious offer to reconstruct a session that needs no reconstruction, plus a
reader of the spec being misled about what the check does.

**Suggested resolution.** Scope the comparison to the **resumption** path only. Step 0c
already distinguishes "resuming an open session branch" from "creating a new session
branch"; Step 5.8's check is meaningful only in the former. Alternatively, make
`.claude/last-wrap-up.txt` the primary signal (it directly records wrap-up completeness and
type) and demote the number comparison to a corroborator, which inverts the current
reliance.

**Note:** Step 5.8's own text says it is "the inverse complement" of the Step 0c
closed-session-leftover case, and that case correctly requires four signals before acting.
Step 5.8 requires one. The asymmetry looks unintentional.
