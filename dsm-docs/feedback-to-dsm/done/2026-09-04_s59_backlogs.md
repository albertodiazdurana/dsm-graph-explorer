## Proposal 1: BACKLOG-543 deleted the Punctuation rule from the §17.1 alignment template and left its three scope paragraphs behind, so every spoke that realigns loses the rule and inherits a headless block

**Type:** Backlog Proposal (content-loss defect)
**Priority:** High

**Problem statement.** `DSM_0.2.T_Alignment_Templates.md` currently contains, between
`### Actionable Work Items` (line 42) and `### Code Output Standards` (line 54), three
paragraphs of rule body with no owning heading. The first opens:

> **Scope.** The rule governs files that reach a reader outside the project, by any
> channel.

"The rule" has no antecedent. The nearest preceding heading is Actionable Work Items,
which the paragraphs do not describe, so a reader parses them as a continuation of it.
The third paragraph closes "An exempt file may be normalized as a one-time tidy", which
points at a normalization rule that is not in the file.

**Provenance.** Three commits, verified with `git log -S` and `git show`:

| Commit | Effect |
|---|---|
| `b1343dd` | BL-469 (v1.17.1) authors the rule: "state punctuation rule as direct em-dash-to-`, `" |
| `387d9f6` | EXP-007 arm A carries it into the extracted template file, at line 82: `### Punctuation` + 2 rule paragraphs + 3 `**Scope.**` paragraphs |
| `daa1619` | BACKLOG-543 (2026-09-01, shipped in **1.26.0**) deletes the heading and BOTH rule paragraphs, and leaves all three scope paragraphs in place |

`daa1619`'s subject is "reword transcript reinforcement to clear the Opus 5 boot-flag".
Its diff against this file is 9 insertions and 48 deletions. The Punctuation removal is
not mentioned in the commit subject, in the CHANGELOG entry for 1.26.0, or in any
`**Spoke action:**` line. It reads as collateral damage inside an unrelated edit rather
than a decision to retire the rule.

**What was lost.** The deleted text, recoverable at `387d9f6:DSM_0.2.T_Alignment_Templates.md`
lines 82-85:

- Paragraph 1: replace a phrase-connecting em dash directly with `, `, in one step, never
  writing the intermediate ` , `. Applies in any language.
- Paragraph 2, which no spoke aligned after v1.18.0 ever received: apply the replacement
  deliberately, not as a blanket character substitution. An em dash joining two
  independent clauses usually wants a period or a semicolon, since a comma there produces
  a splice. An em dash used as a numeric range separator ("30—40 Sek.") must never become
  a comma, because in a decimal-comma locale "30,40 Sek." reads as a decimal, so the range
  is destroyed and the result is still plausible prose.

Paragraph 2 is the half that prevents a wrong fix. Losing it is worse than losing
paragraph 1, because paragraph 1 alone licenses exactly the blanket substitution
paragraph 2 exists to forbid.

**Consequence, and why this is High rather than Medium.** The damage is delivered BY
`/dsm-align`, not by inaction. A spoke that never realigns keeps the rule; a spoke that
does what the CHANGELOG tells it to do loses it. Two 1.26.0 entries carry
`**Spoke action:** Run /dsm-align`, so the fleet is currently being instructed to
propagate the deletion. Each regenerating spoke simultaneously acquires the headless
block, which then looks like intentional template content to the next reader.

**Detection history.** This spoke has not realigned since 1.19.0, so its CLAUDE.md still
carries paragraph 1 and is the last surviving copy of the rule outside git history. The
orphan was noticed only because the regeneration was withheld for an unrelated reason and
the two artifacts were diffed by hand. An agent that accepted the drift report and
regenerated would have reported a clean `/dsm-align` run.

**Verify:**

```bash
cd {dsm-central}
sed -n '42,54p' DSM_0.2.T_Alignment_Templates.md          # heading, orphan, next heading
git show 387d9f6:DSM_0.2.T_Alignment_Templates.md | sed -n '82,88p'   # what was deleted
git show daa1619 -- DSM_0.2.T_Alignment_Templates.md | grep '^-.*em dash'
grep -c 'Punctuation' DSM_0.2.T_Alignment_Templates.md    # 0
```

**Suggested resolution.** Restore `### Punctuation` with both rule paragraphs above the
existing scope paragraphs, and ship it with a `**Spoke action:** Run /dsm-align` so
spokes that already regenerated recover the rule. If the removal WAS intentional, the
three scope paragraphs must be deleted too, and the CHANGELOG should say the rule was
retired, since spokes carrying it in their reinforcement block currently have no way to
learn that.

**Adjacent question, not part of this proposal.** A rule body surviving its heading is a
mechanical outcome that a structural check could catch: any `**Bold.**`-led paragraph
block that follows a bullet list with no intervening `###` heading. Worth considering
only if a second instance appears; one occurrence does not justify a linter.

## Proposal 2: `/dsm-wrap-up` Step 9's mirror self-detection tests for a file that is absent in every non-Central repo, so it classifies every spoke as a mirror

**Type:** Backlog Proposal (logic defect)
**Priority:** Medium

**Problem statement.** `/dsm-wrap-up` Step 9's "Mirror self-detection inbox guard" reads,
verbatim from the deployed skill (`~/.claude/commands/dsm-wrap-up.md`, lines 241-250):

> If `scripts/take-ai-bite-sync.txt` does NOT exist in the current working tree, this repo
> is a mirror (not the hub). Exclude any `_inbox/*` path from the stage-set except
> `_inbox/README.md` and `_inbox/.gitkeep`.

`scripts/take-ai-bite-sync.txt` is the CENTRAL marker. Its absence distinguishes
"not Central" from "Central", which is a two-way test being used to answer a three-way
question. A spoke is not Central, so a spoke tests as a mirror on every wrap-up.

**Consequence.** The guard silently drops legitimate inbox entries from the wrap-up
commit. Measured in this repository on 2026-09-04: `git ls-files _inbox/` returns
**33 tracked files** (S58 measured 32; the archive has grown by one since), so the
premise "mirror repos should not track session-scoped inbox entries" is false here by
33 counterexamples. In S58 the guard would have excluded a real inbox entry from the
commit; it was deliberately not applied. This session created
`_inbox/2026-09-04_dsm-align-update.md`, which the guard would drop, and which now
carries the only working-tree copy of 6 consolidated review items.

The failure is silent in the direction that matters. The guard logs each exclusion as
"Mirror inbox guard: skipped ...", which reads as the guard working correctly, so the
log confirms rather than warns.

**The correct test already exists in the corpus.** `/dsm-go` Step 0.8a resolves this
exact question three ways, deterministically, and is specified as the canonical version
in DSM_0.2.A §25.1: `KICKOFF_DONE` / `CENTRAL` / `SPOKE` / `KICKOFF_NEEDED`. It
distinguishes CENTRAL by the same `scripts/take-ai-bite-sync.txt` marker but then
distinguishes SPOKE from a self-registered hub by comparing the `dsm-central` row in
`.claude/dsm-ecosystem.md` against the repo root. Run at this session's boot, it returned
`SPOKE` for this repository while Step 9's test would return "mirror".

Two steps in the same corpus answer the same question and disagree, which is the stronger
form of this report: the fix requires no new mechanism, only reuse.

**Verify:**

```bash
sed -n '241,250p' ~/.claude/commands/dsm-wrap-up.md    # the guard
git ls-files _inbox/ | wc -l                            # 32 in this repo
# then run /dsm-go Step 0.8a's snippet in the same repo: returns SPOKE
```

**Suggested resolution.** Replace the single-file absence test with Step 0.8a's snippet
and apply the guard only on `CENTRAL`-negative AND mirror-positive, i.e. only where the
ecosystem registry shows this clone self-registered as `dsm-central`. Cheaper interim
fix: invert the guard to opt-in, requiring a positive mirror marker rather than inferring
mirror-ness from an absence.

**Relationship to S58 Proposal 3.** Same family: a check whose premise does not hold in
the repositories it runs in. S58's instance was `/dsm-go` Step 5.8, whose trigger
condition was produced by Step 0a of the same procedure. This one infers a positive
classification from a negative test. Both were found by executing the check against real
state rather than reading it.

## Proposal 3: `/dsm-align` Step 12b writes an inbox notification whose payload lives in a file Step 12a overwrites on the next run, so an unprocessed entry silently comes to point at another run's report

**Type:** Backlog Proposal (notification-design defect)
**Priority:** Medium

**Problem statement.** Two steps of the same skill, 56 lines apart in
`~/.claude/commands/dsm-align.md`, contradict each other.

Step 12a (line 468) writes the payload and declares its lifetime:

> write the full report to `.claude/last-align-report.md` (gitignored, **overwritten each
> run**)

Step 12b (lines 530-546) writes the notification, and its format template hard-codes a
pointer to that same file plus two explicit deferrals to it:

> ```
> Full report: `.claude/last-align-report.md`
> ...
> - Warnings: [count] (see persistent report for full text)
> - Collisions: [count] (see persistent report for full text)
> ```

So the notification is generated by construction as a pointer, the counts are the only
content it retains, and the target is guaranteed to be replaced by the next run of the
same skill. An inbox entry is a durable artifact that waits to be processed; the file it
depends on is explicitly ephemeral. Nothing reconciles the two lifetimes.

**This is not a hypothetical. It happened to three entries in this repository.**

| Entry | Payload destroyed by | Interval |
|---|---|---|
| `2026-07-21_dsm-align-update.md` | the 2026-07-30 `/dsm-align` run (`9799b4e`) | 9 days |
| `2026-07-30_dsm-align-update.md` | this session's 1.26.0 run | 36 days |
| `2026-09-04_dsm-align-update.md` | the next `/dsm-align` run, whenever it happens | pending |

The first two sat unprocessed for 45 and 36 days respectively, and were surfaced at the
start of every session in between as pending inbox items.

**The failure mode is worse than emptiness.** A destroyed payload would at least read as
missing. Instead the pointer keeps resolving: when the 2026-07-21 entry was finally
opened this session, `.claude/last-align-report.md` existed and was well-formed, but
described the **2026-07-30** run. An agent following the pointer gets a complete,
plausible, wrong report, with no signal that the entry and the file describe different
alignment runs. That is the shape DSM_0.2 §19.1 names: "nothing owed" and "could not
look" must not print the same line. Here "the payload" and "a different run's payload"
do not print differently either.

**What the payload actually was, so the loss is concrete.** The 2026-07-21 entry's report
carried five `Review` spoke actions for v1.17.0 to v1.18.0 (DSM_6.0 §1.13; DSM_0.2 §8.10
Gate 4; DSM_0.2.C §2 mirror-sync carve-out, BL-471; DSM_0.1 §10 + DSM_1.0.D §6.4.5,
BL-472; inbox-lifecycle / context-budget / handoff, BL-470). The 2026-07-30 entry's
carried one more (DSM_0.2 §8.9.2, BL-476). Six review items, none of them performed,
none of them reconstructible from the notifications themselves.

**They were recovered only by an accident that the skill's own text denies.** Recovery was
`git show a311190:.claude/last-align-report.md`, which works only because the file is
TRACKED in this repository. Step 12a asserts it is gitignored. Under the contract as
written, the payload would have been unrecoverable and both entries would have been
archived as empty pointers, which is what an agent following the documented behaviour
would have done. The defect was survivable here purely because the documentation is wrong
about the repository, which is not a mitigation anyone can rely on.

**Self-implicating instance, this session.** `/dsm-align` ran at this session's boot and
Step 12b generated `_inbox/2026-09-04_dsm-align-update.md` with the identical
`Full report:` pointer and no payload. It was made durable by hand, by appending the six
recovered review items plus this run's seven directly into the entry. Nothing in the
skill asks for that; the entry as generated carries the same defect as the two it
replaced.

**Verify:**

```bash
sed -n '468p'     ~/.claude/commands/dsm-align.md    # "overwritten each run"
sed -n '530,546p' ~/.claude/commands/dsm-align.md    # the template that points at it
grep -n 'Full report' _inbox/done/2026-07-21_dsm-align-update.md
git log --oneline --since=2026-07-21 -- .claude/last-align-report.md
```

**Suggested resolution.** Make the notification self-contained: have Step 12b inline the
spoke actions, the warning texts and the collision list into the entry rather than
deferring them, and keep the `Full report:` line as a convenience pointer rather than as
the location of the content. The entry is already the right size for it, six items is a
short list, and inlining is what had to be done by hand here anyway.

Cheaper alternative, if inlining is judged too verbose: version the persistent report
(`.claude/last-align-report-{version}.md`, or append rather than overwrite) so an entry's
pointer stays valid. This is strictly worse, because it leaves the notification useless on
its own and grows a file set nothing prunes.

**Relationship to S57 and S58 Proposal 2.** Adjacent but distinct, and deliberately not
folded into them. Those report that skills FALSELY DESCRIBE their state files as
gitignored, a documentation defect. This reports that a durable artifact is built to
depend on an ephemeral one, a design defect. They interact only in the recovery path
above: the documentation being wrong is what made this instance survivable. Fixing either
one alone leaves the other in place, and fixing the gitignore claim by making it TRUE
(reconciling `.gitignore` to match the skills) would remove the only reason the six items
still exist.
